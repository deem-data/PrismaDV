### Critical Guidance on Severity Level (`error` vs `warning`)
The validation framework evaluates data batches against your constraints to catch unsafe/corrupt batches:
- **`level: "error"` is required to flag unsafe batches.** The test harness only considers constraints with `level: "error"` when determining if a batch failure catches unsafe data. If you mark a constraint as `"warning"`, it **will NOT flag unsafe batches**, resulting in zero errors caught and severe penalties to recall and Macro F1.
- **When to use `"error"`**:
  - Any assumption where violation would crash the downstream code (e.g., `ValueError`, `TypeError`, `ZeroDivisionError`, `KeyError`, `.astype()` conversion failure).
  - Any assumption where violation causes invalid, silent data corruption, or breaks core analytical logic (e.g., values out of valid mathematical bounds like inputs to `np.log` or `np.sqrt`, invalid categorical codes, null values where non-null is expected).
  - Even if the code uses defensive constructs like `pd.to_numeric(..., errors='coerce')` or `.fillna()`, if the column's valid presence, type, or bounds are required for correct model execution or downstream downstream logic, set the level to `"error"`.
- **When to use `"warning"`**:
  - Purely advisory, non-critical data quality observations (e.g., subtle distributional drift, loose informational checks) where violating the assumption does NOT corrupt downstream computation or represent an unsafe data batch.
  - **Rule of thumb**: If an assumption defines schema integrity, type correctness, nullability constraints, or valid operational ranges, default to `"error"`.

---

### PyDeequ Function Mapping & Best Practices

1. **Completeness & Nullability**:
   - Must not contain nulls: `.isComplete('column_name')`
   - Completeness threshold: `.hasCompleteness('column_name', lambda x: x >= threshold)`

2. **Data Types**:
   - Use `ConstrainableDataTypes` enum:
     - `ConstrainableDataTypes.Integral` (pure integer values)
     - `ConstrainableDataTypes.Fractional` (floating point values)
     - `ConstrainableDataTypes.Numeric` (union of Integral and Fractional)
     - `ConstrainableDataTypes.String`
     - `ConstrainableDataTypes.Boolean`
   - Example: `.hasDataType('Age', ConstrainableDataTypes.Integral)`

3. **Value Ranges & Bounds**:
   - Non-negative (>= 0): `.isNonNegative('column_name')`
   - Positive (> 0): `.isPositive('column_name')`
   - Explicit range bounds:
     - Use `.satisfies('`col` >= min AND `col` <= max', 'constraint_name')`
     - **CRITICAL**: Always wrap column names in backticks (`` `col` ``) inside the SQL expression to avoid syntax errors with spaces or special characters.
     - Alternatively, use aggregate bounds `.hasMin('column_name', lambda x: x >= min_val)` and `.hasMax('column_name', lambda x: x <= max_val)` if the assumption applies to the column-level extrema.

4. **Regex & String Patterns**:
   - Always use raw strings (`r"..."`) for regex patterns to prevent escape sequence errors.
   - Example: `.hasPattern('Blood Pressure', r'^\d+/\d+$')`

5. **Allowed Values / Categoricals**:
   - Specific set of allowed strings/numbers: `.isContainedIn('column_name', ['val1', 'val2'])`

6. **Uniqueness**:
   - Unique column: `.isUnique('column_name')`
   - Uniqueness ratio: `.hasUniqueness(['column_name'], lambda x: x >= threshold)`
