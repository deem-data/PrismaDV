### Goal & Approach
A good data quality check flags corrupted or invalid batches (unsafe batches) without raising false alarms on normal operational variations (safe batches).

1. **Assert Constraints, Not Permissiveness**:
   - Do NOT write permissive statements like *"The column may contain nulls"* or *"Values can be non-numeric"*. Permissive statements do not produce enforceable Deequ constraints, allowing corrupted batches to pass undetected (high false negatives).
   - Instead, assert the required guarantees:
     - **Completeness**: If the code relies on non-null values (e.g., key generation, formatting, aggregations) or the column profiling shows 100% completeness, assert that the column must be complete (`isComplete`) or maintain high completeness (e.g., at least 80% completeness via `hasCompleteness`).
     - **Data Type**: Assert the expected data type (e.g., `Integral`, `Fractional`, `String`, `Boolean`). Even if the code runs `pd.to_numeric(errors='coerce')`, the pipeline still fundamentally expects the input column to be predominantly of numeric/integral type.
     - **Validity / Range**: Assert reasonable value constraints (e.g., non-negative counts, valid ranges) when required by downstream logic.

2. **Account for Defensive Code to Prevent False Alarms**:
   - Do NOT assert strict value sets (`isContainedIn`) if the code already includes defensive handling (e.g., `.where(isin(...), other=np.nan).fillna(...)` or fallback branches). Imposing strict containment on sanitized columns often fails on valid edge cases (high false positives).
   - Reserve strict categorical or containment assertions for cases where unexpected values would break the code or pipeline logic.

3. **Leverage Column Profiling Metadata**:
   - Use `target_column_desc` (completeness, approximateNumDistinctValues, dataType, typeCounts) alongside the code to determine baseline expectations. If a column is profiled as 100% complete and Integral, assert these core properties.

4. **Source Attribution**:
   - Map each assumption to the specific line ranges (`start_line` to `end_line`) in the provided code snippet where the column is read, transformed, or assumed to have specific characteristics.

### Guidelines for Constraint Design & Level Assignment

#### 1. Deciding Between "error" and "warning" (CRITICAL)
The verification suite evaluates batches of data. **Only constraints marked with `level: "error"` will fail a batch and flag it as unsafe.** If you set constraints to `"warning"`, PyDeequ will treat them as informational only and will NOT catch unsafe batches, leading to zero error detection and severe recall penalties.

- **Set `"level": "error"`** when:
  - Violating the assumption would cause runtime crashes (e.g., `KeyError`, `ValueError`, `TypeError`, `ZeroDivisionError`, `IndexError`) in the script. Examples include missing required columns, unexpected `NaN` values fed into `int()` / `.astype(int)`, unhandled regex extract failures, or non-numeric types in numeric calculations.
  - The column is essential for the core pipeline logic or final output, and invalid values (e.g., out-of-range ratings, wrong types, missing primary keys) invalidate the output even if pandas operations partially coerce or handle nulls.
  - The check is the primary guardrail detecting corrupted/unsafe batches for that column.
  
- **Set `"level": "warning"`** ONLY when:
  - The script explicitly has robust, intentional fallback handling (e.g., `.fillna('NR')`, `.replace()`, optional display fields) AND the data anomaly does not compromise downstream processing.
  - The check is a soft statistical or data quality sanity check (e.g., slight distribution shifts, optional metadata fields).

*Do NOT default to `"warning"` merely because Pandas provides methods with `errors='coerce'` or `.fillna()` if the assumption represents a critical data contract.*

#### 2. Calibrating with `target_column_desc` to Avoid False Alarms
- **Completeness**: 
  - If `target_column_desc.completeness < 1.0`, do NOT use `.isComplete('col')` (this will trigger false alarms on safe data). Instead, use `.hasCompleteness('col', lambda x: x >= threshold)` where `threshold` is reasonably set slightly below the baseline completeness (e.g., baseline 0.898 -> threshold 0.80 or 0.85).
  - If `completeness == 1.0` and the code does not handle nulls, use `.isComplete('col')`.
- **Data Types**:
  - Always check `typeCounts` and `dataType`. For columns containing both integers and floats, use `ConstrainableDataTypes.Numeric` rather than `Integral` or `Fractional`.
- **Categorical Sets**:
  - For `isContainedIn`, verify against `approximateNumDistinctValues` and known categories. If unknown/missing categories exist in baseline data, add an assertion threshold (e.g., `lambda x: x >= 0.95`) or include default values (e.g., 'Not Rated', 'NR') to avoid false alarms.

#### 3. Syntax and Function Rules
- Constraints must start with `.` (e.g., `.isComplete('column')`).
- In `satisfies(condition, name)`, write the condition as a SQL WHERE clause using backticks for column names (e.g., ``'`IMDB_Rating` >= 0 AND `IMDB_Rating` <= 10'``).
- In `hasPattern`, always use Python raw string notation (e.g., `r"^\d+$"`).
- In `hasDataType`, use `ConstrainableDataTypes.<Type>` from `pydeequ.checks.ConstrainableDataTypes` (`Null`, `Fractional`, `Integral`, `Boolean`, `String`, `Numeric`).
