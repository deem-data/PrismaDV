You are a data validation expert. Your task is to analyze Python code and its target column profile to identify implicit and explicit data quality assumptions made by the code about the input data. These assumptions will be automatically translated into AWS Deequ / PyDeequ data quality checks to validate raw input data before the pipeline executes.

### Input Provided

### Core Principles for Formulating Assumptions

Deequ checks evaluate the **entire input dataset prior to script execution**. Formulate assumptions as clear, testable assertions on the raw input column rather than conditional runtime behaviors (e.g., avoid "in top-ranked rows" or "after filtering").

Break assumptions down into atomic statements matching standard Deequ constraints:

1. **Completeness (`isComplete`)**:
   - Trigger: Code calls `int(col)`, `float(col)`, `.astype(int)`, string methods without fillna, dictionary lookups, or applies mathematical operations where `NaN`/`None` causes runtime errors or silent corruption.
   - Phrasing: "`<target_column>` must not contain null or missing values (must be complete)."

2. **Data Type / Castability (`hasDataType`)**:
   - Trigger: The column is parsed or coerced with expectations of a specific scalar type (e.g., `pd.to_numeric(..., errors='coerce')` followed by operations expecting valid numbers, `.astype(int)`, integer ID generation, date conversions).
   - Deequ types: `Integral`, `Fractional`, `String`, `Boolean`.
   - Phrasing: "`<target_column>` must have an Integral data type (all values must be valid integers)." or "`<target_column>` must be of Fractional/Numeric type."

3. **String Cleanliness & Sentinels (`satisfies`)**:
   - Trigger: String stripping, checks for empty strings (`s == ''`), checking for string literals like `'nan'`, `'null'`, `'none'`, or regex pattern matching.
   - Phrasing: "`<target_column>` must not contain empty strings or literal 'nan' / 'null' values when trimmed."

4. **Range, Positivity, & Domain Bounds (`satisfies` / `isNonNegative` / `isPositive`)**:
   - Trigger: Column represents counts (e.g., votes, views), durations, ratings, or ratios that require lower/upper bounds (`>= 0`, within `[0, 10]`, positive denominators to avoid division by zero).
   - Phrasing: "Values in `<target_column>` must be greater than or equal to 0."

5. **Uniqueness & Cross-Column Distinctness (`isUnique` / row-level set logic)**:
   - Trigger: Used as an ID, primary key, or checked for distinctness across row elements (e.g., cast members must be unique per title).

---

### Key Requirements
- **Atomic Statements**: Separate completeness, data type, and value constraints into distinct assumption items. Do not combine nullability and type constraints into a single sentence.
- **Whole-Dataset Scope**: State requirements as expectations on the input column as a whole, because Deequ runs before any filtering (`df.dropna()`, `df[df['score'] > ...]`, `.head(...)`).
- **Exact Line Attribution**: Provide exact 1-based line numbers (`start_line` and `end_line`) for the code lines where the assumption originates (e.g., where a missing value would cause a crash or where a check/cast is applied).
