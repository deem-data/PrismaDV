### Constraint Types and PyDeeQu Syntax Guidelines

Generate rules using standard PyDeeQu constraint method calls. Every rule must be formatted as a method call string starting with a dot (`.`):

1. **Completeness Check**:
   - Method: `.isComplete('<column_name>')`
   - Trigger: Assert this whenever the column is read, type-cast (e.g., `.astype(float)`, `pd.to_numeric`), filtered, or used in arithmetic without handling `NaN`/`null`.

2. **Data Type Check**:
   - Method: `.hasDataType('<column_name>', ConstrainableDataTypes.Numeric)`
   - Trigger: Assert when the column is treated as numeric (floats/integers for arithmetic, comparisons, sums, or scalings).

3. **Non-Negativity Check**:
   - Method: `.isNonNegative('<column_name>')`
   - Trigger: Assert for numeric attributes that logically cannot be negative (e.g., grades, admission scores, credits, age, counts).

4. **Discrete Set / Categorical Membership**:
   - Method: `.isContainedIn('<column_name>', ['<val1>', '<val2>', ...])`
   - Trigger: Assert when the column is treated as a binary or categorical flag (e.g., checked against `== 0` or `== 1`). Values in the array should be string representations (e.g., `['0', '1']`).

5. **Range / SQL Predicate Satisfiability**:
   - Method: `.satisfies('<sql_condition>', '<assertion_name>')`
   - Trigger: Assert when the code relies on specific domain bounds, clip limits, or normalizations.
   - Important syntax rules:
     - Column names inside the SQL condition containing spaces or special characters must be enclosed in backticks (`` `column_name` ``).
     - The second argument must be a descriptive snake_case identifier for the assertion.
   - Common patterns:
     - Bounded range: `.satisfies('`<column_name>` >= <min> AND `<column_name>` <= <max>', '<name>')`
     - Upper/Lower bound: `.satisfies('`<column_name>` <= <max>', '<name>')`
