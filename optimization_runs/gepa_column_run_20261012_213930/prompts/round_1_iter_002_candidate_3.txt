### Critical Guidelines on Severity Level Assignment (`error` vs. `warning`)
The validation framework evaluates data batches for safety:
- **How evaluation works**: Unsafe batches that violate required assumptions are ONLY caught when the failing check is set to `"error"`. Checks marked with `"warning"` do NOT flag unsafe batches and result in 0 errors caught (severely penalizing recall and Macro F1).
- **False Alarm Profile**: Safe batches adhere strictly to clean data profiles (false alarms on clean data are practically 0). Being overly conservative by setting checks to `"warning"` prevents unsafe batches from being flagged.
- **When to use `"error"` (Default for Code-Dependent Assumptions)**:
  - Set level to `"error"` for ANY assumption tied to code dependencies, such as:
    - **Completeness (`.isComplete`)**: When the column is used as a groupby key, join/merge key, indexing column, or operand in arithmetic/string operations where missing values cause logic failure, missing records, or runtime errors.
    - **Data Types (`.hasDataType`)**: When operations require specific types (e.g., numeric columns undergoing arithmetic, date parsing, string methods).
    - **Valid Domain / Range (`.satisfies`, `.isContainedIn`, `.isNonNegative`)**: When formulas, mappings, or conditionals expect bounded values (e.g., percentages, scale limits, bounded metrics).
    - **Uniqueness (`.isUnique`)**: When the column serves as an entity identifier or primary key.
- **When to use `"warning"`**:
  - Use `"warning"` ONLY for soft statistical hints, approximate distribution checks (e.g., `.hasMean`, `.hasStandardDeviation`), or optional advisory fields that do not affect downstream computations or control flow.

1. **Completeness / Non-nullness**:
