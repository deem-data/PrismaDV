### Critical Severity Rules ("error" vs "warning")
Setting severity correctly is critical for pipeline safety and data validation benchmarks:
- **Set level to `"error"` (Default for pipeline requirements):**
  - Use `"error"` whenever a violation compromises data integrity, violates schema/type constraints, introduces unexpected nulls into downstream calculations, breaks mappings, or produces invalid downstream outputs (such as corrupting risk scores, metrics, financial adjustments, or model training).
  - Do NOT restrict `"error"` strictly to code that throws an unhandled Python exception. Silent data corruption (e.g., unhandled NaNs propagating through arithmetic, unmapped dictionary keys becoming NaN, invalid categorical levels, or negative values where only positive values make mathematical sense) makes a data batch unsafe and MUST be caught with `"error"`.
  - Always set `"error"` for:
    - Schema & Data Type conformance (`hasDataType`).
    - Completeness requirements when nulls break downstream math or mapping (`isComplete`, `hasCompleteness`).
    - Value domains / Allowed categories (`isContainedIn`).
    - Relational bounds and validity (`isNonNegative`, `isPositive`, `isLessThanOrEqualTo`, `satisfies`).
    - Uniqueness or Primary Key constraints (`isUnique`).
- **Set level to `"warning"` ONLY when:**
  - The script explicitly and safely handles the anomaly (e.g., deliberate, intentional fallback values that produce valid outputs).
  - The assumption relates to soft statistical drift, non-critical distribution checks, or minor data quality warnings that do not invalidate the results.

---

### Function Selection and Syntax Guidelines
1. **Method Chaining Syntax:**
   - Every suggestion string must begin with a dot `.` representing method chaining on a PyDeequ `Check` object (e.g., `".isComplete('col')"`).
2. **Strict Function Catalog Adherence:**
   - Use ONLY functions listed in the provided catalog.
   - Do NOT invent functions that do not exist (e.g., do not use `.isBetween()`; instead, use `.satisfies('`col` >= min AND `col` <= max', 'col_range')` or separate `.hasMin` / `.hasMax` / `.isGreaterThanOrEqualTo`).
3. **Data Types:**
   - When using `.hasDataType(column, datatype)`, `datatype` MUST be an enum from `ConstrainableDataTypes`:
     - `ConstrainableDataTypes.Numeric`
     - `ConstrainableDataTypes.Integral`
     - `ConstrainableDataTypes.Fractional`
     - `ConstrainableDataTypes.String`
     - `ConstrainableDataTypes.Boolean`
     - `ConstrainableDataTypes.Null`
4. **Regular Expressions:**
   - Always format regex strings in `.hasPattern(column, pattern)` as raw strings (e.g., `r"^\d+$"`).
5. **SQL Conditions in `.satisfies`:**
   - Use SQL WHERE syntax and quote column names with backticks (e.g., `".satisfies('`Age` >= 18', 'age_min_18')"` or `".satisfies('`YearsSinceLastPromotion` <= `YearsAtCompany`', 'promotion_le_company_tenure')"`).
6. **Correct Argument Types:**
   - Pay close attention to single column vs list of columns:
     - `.isUnique('col')` takes a string.
     - `.hasUniqueness(['col'], lambda x: x >= 0.99)` takes a list.
     - `.areComplete(['col1', 'col2'])` takes a list.
     - `.isComplete('col')` takes a string.
7. **Assumption Linking:**
   - Each constraint in `constraint_code` must include the exact 0-based indices of all assumptions it directly verifies in `linked assumptions`.
   - Every verifiable assumption should be mapped to at least one constraint check.
